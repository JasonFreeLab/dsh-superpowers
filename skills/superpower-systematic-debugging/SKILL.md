# 系统化调试（Systematic Debugging）

## 概述

**核心原则：** 在尝试修复之前，永远先找到根因。修症状就是失败。

**违反本流程的条文，就是违反调试的精神。**

## 铁律

```
没有先做根因调查，就不允许提出修复
```

如果你还没完成阶段 1，就不能提出修复。

## 何时使用

任何技术问题都用：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况必须用：**
- 时间压力下（紧急情况让人想猜）
- "就一个快速修复"看起来很显然
- 你已经试过多个修复
- 之前的修复没奏效
- 你并不完全理解这个问题

**不要跳过，即使：**
- 问题看起来简单（简单的 bug 也有根因）
- 你很赶时间（仓促必然返工）
- 经理要求立刻修好（系统化比乱试更快）

## 四个阶段

进入下一阶段前，你必须完成当前阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的答案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 不能复现 → 收集更多数据，不要猜

3. **检查最近的变更**
   - 什么变化可能导致这个？
   - `git diff`、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **多组件系统中收集证据**

   **当系统有多个组件（CI → 构建 → 签名，API → 服务 → 数据库）时：**

   **在提出修复之前，添加诊断插桩：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每一层的状态

   先运行一次收集证据，看它在哪一环断开
   然后分析证据，找出失败的组件
   然后调查那个具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈里时：**

   完整的向后追踪技术见本目录下的 `root-cause-tracing.md`。

   **简版：**
   - 坏值从哪来？
   - 是谁带着坏值调用了这里？
   - 一直往上追，直到找到源头
   - 在源头修，不在症状处修

### 阶段 2：模式分析

**修复之前先找模式：**

1. **找能工作的例子**
   - 在同一个代码库里找类似的能工作的代码
   - 什么能工作、且和坏的东西相似？

2. **对照参考实现**
   - 如果在实现某个模式，完整阅读参考实现
   - 不要略读——逐行读
   - 在应用之前彻底理解该模式

3. **找出差异**
   - 能工作的和坏掉的之间差什么？
   - 列出每个差异，不管多小
   - 不要想当然"那不可能有关系"

4. **理解依赖**
   - 它需要哪些其它组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **形成单一假设**
   - 清楚地说："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 做最小可能的变更来验证假设
   - 一次只变一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 有用吗？是 → 阶段 4
   - 没用？形成新假设
   - 不要在上面叠加更多修复

4. **当你不懂时**
   - 说"我不理解 X"
   - 不要装懂
   - 寻求帮助
   - 继续研究

### 阶段 4：实施

**修根因，不是修症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 尽量自动化测试
   - 没有框架就写一次性测试脚本
   - 修复之前必须有
   - 编写规范的失败测试时，通过 `skill` 工具加载 `superpower-test-driven-development` 技能

2. **实施单一修复**
   - 针对已识别的根因
   - 一次只改一处
   - 不要"顺手"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其它测试坏掉？
   - 问题真的解决了吗？
   - 声称成功之前，通过 `skill` 工具加载 `superpower-verification-before-completion` 技能

4. **如果修复无效**
   - 停下
   - 数一数：你试过几个修复了？
   - 如果 < 3：带着新信息回到阶段 1 重新分析
   - **如果 ≥ 3：停下，质疑架构（见下面第 5 步）**
   - 未经架构讨论，不要尝试第 4 个修复

5. **3 次以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同的地方暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都在别处制造新症状

   **停下，质疑根本：**
   - 这个模式从根本上说得通吗？
   - 我们是不是"纯粹靠惯性死撑"？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，与你的人类搭档讨论**

   这不是假设失败——这是架构错误。

## 危险信号 - 停下并按流程走

如果你发现自己想：
- "先快速修一下，以后再调查"
- "就试着改改 X 看行不行"
- "加多处修改，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，让我修它"
- "我不完全懂，但这个可能行"
- "模式说是 X，但我要换个方式改编它"
- "主要问题如下：[列出修复，没有调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经试过 2 次以上时）**
- **每次修复都在不同的地方暴露新问题**

**所有这些都意味着：停下。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 你的人类搭档发出"你做错了"的信号

**留意这些纠正：**
- "那不是没发生吗？" - 你没验证就假设了
- "它会给我们看到……吗？" - 你本该加证据收集
- "别猜了" - 你在没理解的情况下提修复
- "往深处想" - 质疑根本，而不只是症状
- "我们卡住了？"（沮丧） - 你的方法不管用

**看到这些时：** 停下。回到阶段 1。

## 常见自我合理化

| 借口 | 现实 |
|--------|--------|
| "问题很简单，不需要流程" | 简单的问题也有根因。对简单的 bug，流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比瞎猜乱试更快。 |
| "先试试这个，然后再调查" | 第一个修复定下基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 没测试的修复留不住。测试先行证明它。 |
| "一次修多个省时间" | 无法隔离哪个起作用了。还会制造新 bug。 |
| "参考太长，我改编一下模式" | 一知半解必然出 bug。完整读它。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，别再修了。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解是什么（WHAT）和为什么（WHY） |
| **2. 模式** | 找能工作的例子、对照比较 | 找出差异 |
| **3. 假设** | 形成理论、最小化验证 | 假设被证实，或形成新假设 |
| **4. 实施** | 建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示"没有根因"时

如果系统化调查揭示问题确实是环境性的、时间相关的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误信息）
4. 添加监控/日志供未来调查

**但是：** 95% 的"没有根因"案例都是调查不完整。

## 配套技术

这些技术是系统化调试的一部分，位于本目录：

- **`root-cause-tracing.md`** - 沿调用栈向后追踪 bug，找到原始触发器
- **`defense-in-depth.md`** - 找到根因后，在多层添加校验
- **条件等待（condition-based waiting）** - 用条件轮询取代任意超时：不要 sleep 固定时长，而是轮询直到条件满足或超时（本移植版未单独成文）
