# 完成前的验证（Verification Before Completion）

## 概述

**核心原则：** 永远先有证据，再有断言。

**违反本规则的条文，就是违反本规则的精神。**

## 铁律

```
没有新鲜的验证证据，就不允许声称完成
```

如果你没有在本条消息里运行验证命令，你就不能声称它通过。

## 门控检查（Gate Function）

```
在任何状态声明或表达满意之前：

1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（新鲜的、完整的）
3. 读取：完整输出，检查退出码，数失败数
4. 验证：输出确实支持该声明吗？
   - 否：带着证据陈述实际状态
   - 是：带着证据陈述声明
5. 然后才：做出声明

跳过任何一步 = 说谎，不是验证
```

## 常见失败

| 声明 | 需要 | 不够充分 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、"应该能过" |
| Lint 干净 | Lint 输出：0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令：exit 0 | Lint 通过、日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 改了代码、假定已修 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过一次 |
| 代理已完成 | VCS diff 显示变更 | 代理报告"成功" |
| 需求已满足 | 逐行核对清单 | 测试通过 |

## 危险信号 - 停下

- 使用"应该""大概""似乎"
- 在验证之前表达满意（"太好了！""完美！""搞定！"等）
- 没有验证就要提交/推送/开 PR
- 轻信代理的成功报告
- 依赖部分验证
- 心想"就这一次"
- 累了，想让工作赶紧结束
- **任何没有运行验证就暗示成功的措辞**

## 合理化预防

| 借口 | 现实 |
|--------|--------|
| "现在应该能过了" | 运行验证 |
| "我很确信" | 确信 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Lint 过了" | Lint ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "我累了" | 疲惫不是借口 |
| "部分检查就够了" | 部分什么也证明不了 |
| "换种说法所以规则不适用" | 重精神胜于重条文 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到: 34/34 通过] "所有测试通过"
❌ "现在应该能过了" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 写 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 还原 → 运行（通过）
❌ "我写了回归测试"（没有做红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到: exit 0] "构建通过"
❌ "Lint 过了"（Lint 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**代理委派（DSH 中对应 `subagent` / `subagent_fork` 委派的子代理）：**
```
✅ 代理报告成功 → 检查 VCS diff（git diff）→ 验证变更 → 报告实际状态
❌ 轻信代理报告
```

## 何时应用

**以下情况之前永远要：**
- 任何形式的成功/完成声明
- 任何满意表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、完成任务
- 进入下一个任务
- 委派给代理

**规则适用于：**
- 确切的措辞
- 转述和同义词
- 对成功的暗示
- 任何暗示完成/正确的交流
